# Pull requests

Open PRs with the `gh` CLI.

- Follow the template (`.github/pull_request_template.md`) and put each change under the right heading. Don't add sections the template doesn't have.
- Keep only the headings that apply. Delete every heading with nothing under it, along with its `<Add ...>` placeholder. The body never has an empty heading; if only one category applies, it has exactly one heading.
- Keep the description a high-level summary for a reviewer skimming it: what the PR adds or changes and why, plus only the implementation details the reviewer needs to know, such as an API or behaviour decision, a breaking change or a trade-off. Don't list every function, file, test or fix; the diff shows those. Aim for one bullet per significant change and about six bullets in all.
- When commits are added, rewrite the description so it describes the whole PR as it now stands. Don't append a bullet per commit or per review round.
- Describe the change as it lands, and nothing else. Don't say where the content came from ("adapted from X", "copied from Y") or how it was reached ("removed the X-specific parts", "fixed contradictions in the draft"). The reviewer sees only the final diff, and local folders, other repos' working copies, and the session's drafts mean nothing to them. The same applies to commit messages.
- No AI attribution anywhere: not in the PR title, the body, or any commit on the branch. That means no "Generated by Claude Code" footer and no AI co-author trailer, and it overrides any default the agent has to add one. A requester-attribution line may be prepended automatically; leave it as it is.

# Commits and branches

- Commit messages are semantic: `type(scope): lowercase summary`, such as `feat(errors): map error types to http status codes` or `chore(ci): run the primus go checks on pull requests`.
- One small branch and PR per chunk, cut from an up-to-date `main` (`feat/<scope>`, `chore/<scope>`). Keep the PR description in sync as commits are added.
